## Method

- **Reference.** UCanAccess 5.1.8 (with Jackcess 5.1.7 and HSQLDB 2.7.4) ran every kept query of the Access database on a read-only copy built from each dataset. Its outputs, recorded once, are the goldens. UCanAccess is an independent engine, not Microsoft Access: where it evaluates a function differently from Access, the goldens carry that difference. Units whose queries call such functions are flagged needs_access_confirmation and listed under Known differences.
- **Datasets.** The engagement dataset (the original application's own data, kept on our side) and 3 synthetic datasets (seed-1, seed-2 and seed-3), generated from the data model and committed in `goldens/synthetic/`.
- **Databases.** The new application ran every unit on PostgreSQL (primary) and SQL Server.
- **SQL Server.** SQL Server cells come from local runs in Docker (mp-mssql22). The target repository's CI runs the harness on the synthetic seeds as a cross-check only; its results are not part of this report.
- **Canonical form.** Every output is put into canonical form version 1 (typed values, fixed number and date formats, normalised row order) before it is compared.
- **Comparison.** Synthetic outputs are compared file by file with the committed expected files. Engagement outputs are compared by HMAC-SHA256 digest of their canonical bytes with the digest in `goldens/manifest.json`; the key is derived from the original data file, so the outputs themselves never leave our side.
- **Redaction.** Failure output on the engagement data is redacted: the terminal and the JUnit files show only the unit, the number of differing rows and the column names; the detail stays in our private logs.
- **Pass rate.** A cell's rate is passed / |C_d|, where C_d is the kept units characterized (status ok) on that dataset. Failed, error, skipped and not-implemented outcomes count as not passed.

## How to re-run

**Synthetic seeds (anyone, any machine, CI included).** The harness is vendored in `equivalence/` and runs without our toolkit. From `app/`, one cell at a time:

```
uv run python -m pytest -c pyproject.toml --rootdir . ../equivalence/tests -p equivalence.plugin \
  --create-db --eq-adapter ../equivalence/adapter.toml --eq-dataset seed-1 --eq-db postgresql \
  --junitxml junit-equivalence-seed-1-postgresql.xml -p no:cacheprovider
```

Repeat with `--eq-dataset` `seed-1`, `seed-2` and `seed-3` and `--eq-db` `postgresql` and `mssql`. `equivalence/README.md` explains the server URL variables and the options.

**Rule and end-to-end tests.** From `app/`: `uv run pytest -q --create-db` runs the whole suite, end-to-end tests included, on the database in `DATABASE_URL`; on SQL Server add `--ignore=tests/e2e`.

**Engagement dataset.** Its goldens and outputs hold your data, so it runs only on our side, through our data plane (`mp-data equivalence <records>/engagement.json --adapter django --datasets all --dbs from-engagement --min-pass-per-cell 0.9`), with redacted output. You can re-run it on your own copy of the data as `equivalence/README.md` describes under Re-running on your own data.

**This report.** `mp-data results summarize` turns the JUnit files of a full run into `equivalence/results.json`; `toolkit report <records>/engagement.json --results equivalence/results.json --out docs/equivalence-report.md` renders this file, and `--check` confirms it is current.
